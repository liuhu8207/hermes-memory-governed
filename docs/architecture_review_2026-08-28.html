一、P1 · 架构闭环缺口（最值得先做）

① L2 ↔ L3 关联缺失：audit 溯源断链
_sync.py :: _extract_atomic_facts / _recall.py :: audit 链路
L2 记录只有 content/category/source/timestamp，没有指向 L3 消息的引用。governed_audit 查到 L2 后无法下钻到原始对话——「这条记忆是哪次对话提取的」不可追溯。
建议：L2 schema 加 source_ref（L3 消息 id + session_id），audit 工具支持 L2 → L3 下钻。改动小（建表 + 写入 + audit 各一处）。
② L2 无重建机制：事实源与派生索引脱钩
scripts/（无 l2_rebuild）
L3 是事实源，L2 是派生索引——但只有 NULL vector 迁移，没有从 L3 全量重建 L2 的入口。L2 表损坏、模型更换、提取逻辑升级时无法恢复。
建议：加 scripts/l2_rebuild.py（从 L3 重提取事实 → 重建表），可 cron 兜底。这也是「L2 坏了随时能回来」的架构保障。
③ Bridge 是死胡同：审查通过后无处落地
_bridge.py :: import_to_scope_recall（TODO，只计数不写）
自动提取的记忆候选写入 candidates.jsonl 后没有消费方：import_to_scope_recall 只计数；审查通过的候选无法自动进入 L1 或 Scope Recall。整条「提取 → 审查 → 落地」闭环缺最后一环。
建议（二选一）：① 实现 import（审查通过 → 写回 L1 文件或 Scope Recall 库）；② 明确「人工导出」定位，文档写明导出 → 手动入库流程，并把 import 方法标记为 not-implemented 而不是半成品。

二、P2 · 可靠性 / 演进

① Embedding 模型与维度硬编码（换模型 = 改 4 处 + 重建表）
_sync.py / _recall.py（all-MiniLM-L6-v2）· _sync.py 建表（384 固定）
模型名硬编码两处、维度 384 硬编码在 PyArrow schema——换 embedding 模型要改 4 处，且旧表因维度不同不兼容（必须重建）。
建议：config 化 vector.model + vector.dim；建表用 dim，加载用 model 名。未来换模型 = 改配置 + 重建索引（配合建议②）。
② L3 无限增长，无保留策略
_sync.py :: L3Writer（messages 只增不减）
messages + messages_fts 只增不减，长期运行磁盘与检索性能都会恶化。
建议：cron 保留策略——保留最近 N 天（如 180 天），更早的旧消息若已提取进 L2 可压缩为摘要或删除；与建议②的 l2_rebuild 配合，L3 清理不丢知识。
③ 写路径无幂等：重复 sync_turn 产生重复归档
_sync.py :: L3Writer.write（无消息级去重）
同一 session 重复 sync_turn（对话重放、故障重试、宿主 bug）会重复写入 L3，FTS 检索时同内容多条命中。
建议：messages 表加 (session_id, content_hash) 唯一约束或写入前去重（INSERT OR IGNORE）。

三、P3 · 观测性

事项现状建议
prefetch 缓存命中率无统计recall_status 只报最后一次召回条数加命中/未命中计数器——判断 TTL（30s）与预取查询是否有效，命中率过低说明预取策略要调
health 报告无趋势单次快照对比上次报告（L2/L3 行数增量、Bridge 候选增长、提取率）——让「记忆在增长还是停滞」可见
配置无类型校验JSON 解析失败才 warning，类型错误（如 token 预算写成字符串）静默生效启动时对关键数值字段做类型校验并 warning

四、不建议动的既有设计（多轮实测打磨的结果）

L3 同步写 / L2 异步写
事实源必须同步保数据安全，派生索引异步可重建——数据丢失风险的架构级权衡，正确。
独立临时池 + shutdown(wait=False)
并发隔离 + 不阻塞 + 无泄漏，三目标同时满足（经历过共享池退化与 with 阻塞两轮教训）。
组内 min-max 归一化 + MIN_SCORE 阈值
L2/L3 量纲统一（差 6 个数量级），阈值安全、组内最强恒可见——方向修正后已稳定。
中文 LIKE 降级
FTS5 默认分词器不切中文（实测），LIKE 是唯一不依赖分词器的可靠方案；英文仍走 FTS5。
Bridge 追加 + 去重 + 归档
并发安全 + 防重复 + 防无限增长，三条同时满足。

优先级建议：先做 P1 的 ①②（L2 关联与重建，小改动大保障）和 ③ 的定位明确（决定 Bridge 的未来）；P2 的 ①（模型 config 化）在下次换模型前做即可；其余按需。

二、新引入的并发问题（实测确认）

新问题 1共享池并发退化：慢任务未完成时，重叠召回返回空结果
_recall.py :: parallel_recall + __init__（共享 self._pool, max_workers=3）
3 个 worker 恰好对应 3 个 layer。第一次召回超时后慢任务仍占满 3 个 worker，此时第二次召回的 3 个任务排队等待，as_completed 的超时计时包含排队时间 → 第二次召回在窗口内一个任务都没跑完 → 返回空。queue_prefetch 每轮起后台线程调 parallel_recall，用户快速连续对话（间隔 < 慢任务耗时）即触发；governed_search 工具连续调用同理。影响：召回结果不完整（prefetch 有 L1-only 兜底，不崩），不影响正确性。
实测（慢任务 2s，超时 0.5s）： 第1次召回: 0.51s, 结果 ['P4'] ← 3 慢任务占满 worker 第2次召回(重叠): 0.50s, 结果 [] ← 任务排队，全部超时 ← 退化 第3次召回(无重叠): 0.51s, 结果 ['P4'] ← 恢复正常
修复建议：max_workers 提到 6+（两轮召回不互相挤占）；或改回每轮新建池 + shutdown(wait=False)（已验证无线程泄漏，GC __del__ 兜底）。
新问题 2shutdown() 后再调用 parallel_recall 直接崩溃
_recall.py :: shutdown / parallel_recall
shutdown() 把 self._pool = None，但 parallel_recall 没有对 None 做防御——shutdown 后任何 recall 调用（如宿主关停顺序问题、延迟完成的后台线程）抛 AttributeError: 'NoneType' object has no attribute 'submit'。
实测：shutdown() 后 parallel_recall('x') → AttributeError: 'NoneType' object has no attribute 'submit'
修复建议：parallel_recall 开头 if self._pool is None: 同步执行或重建池。
运维Bridge JSONL 追加模式 → 文件无限增长
_bridge.py :: export_candidates
覆盖改追加后 candidates.jsonl 会持续增长（去重只防同内容重复写入，不清理旧条目）。建议在 daily pipeline 里加归档/清理步骤（如按 updated_at 保留最近 N 天）。

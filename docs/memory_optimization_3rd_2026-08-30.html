一、P1 · 检索质量（最值得做，都是小改动）

#优化点现状与问题方案与收益
1L2 内容级去重（写入 + 检索）压测确认：同内容跨 session 各写一条 L2 fact（source_rowid 不同）；检索时重复内容重复注入、白白占 L23 预算写入期按 content 查重（保留首次 source_rowid）；检索期按 content 去重保留最高分。预算使用率立涨
2L2 双路径分数语义统一向量路径 score=1.0−距离（相似度语义）；文本降级 score=0.5+命中数×0.1（匹配度语义）——两种分数混排后排序失真统一为相似度语义，或各自归一化后再合并。修复排序失真
3promote 已批准模式跳过候选被 import_approved 落地 L1 后，下次 promote 仍会生成相同候选（只查 L3 重复，不查已批准记录）——重复推荐import_approved 记录已晋升模式（content 归一化指纹），promote 时跳过
4L2 空结果跨层补偿L2 无命中直接空，不利用 L3 的相关检索兜底（L3 只在并行召回里并列检索）低价值，可跳过（并行召回已天然覆盖）

二、P2 · 生命周期 / 数据一致性

#优化点现状与问题方案与收益
1启动时增量索引自愈L3 是事实源、L2 是派生索引；进程退出前异步队列未处理完 → L2 缺数据且无人知晓（只能手动 l2_rebuild）启动时对比 L3 最大 rowid vs L2 最大 source_rowid，有缺口打 warning + 提示/自动增量补索引。最大的数据一致性缺口
2基于使用反馈的排名排名靠「重复次数」（promote）和静态分数，没有「agent 是否真的用到这条记忆」的反馈闭环recall 注入后记录被引用信号（输出中出现记忆关键词），累计 usage 计数参与排序加权——用得多的记忆自动浮上来（OpenSquilla 浮现机制的实质）
3L1 大小治理import_approved 不断向 MEMORY.md 追加、无预算管控；超预算只截断注入、文件本身无人治理health 报告加 L1 字节/token 数与超预算告警，配合定期人工精简提示

三、P3 · 打磨项

#优化点说明
1FTS5 trigram tokenizerSQLite 3.34+：中文检索从 LIKE 升级 trigram，性能与精确度提升（需重建 FTS 表——migrations 机制可挂）
2dream 空闲触发会话空闲时自动跑 dry-run 预览（现在是纯 cron）
3L2/L3 混排权重微调L3 组内最强恒 1.0 与 L2 绝对分混排；可给 L3 加 0.9 层权重上限（历史归档略低于语义记忆的语义表达）

四、建议与理由

优先级事项理由
先做P1 的 ① 内容去重 ② 分数语义统一 ③ promote 防重复都是小改动，直接提升「上下文预算利用率和推荐质量」，且有压测场景可回归
规划P2 的 ① 启动自愈 ② 使用反馈排名记忆系统从「好用」到「会进化」的分水岭；使用反馈排名是 OpenSquilla 浮现机制的本地化实现
按需P3 全部性能/体验打磨，不阻塞使用

备注：L2 缺数据自愈与使用反馈排名若落地，建议都先以「dry-run / 预览 + warning」形式上线（延续项目一贯的 safety-first 风格），确认行为后再自动化。

一、结论先行

OpenSquilla 的优势：记忆生命周期自动化 + 轻量嵌入

四层认知记忆（工作/情节/语义/原生）配上「浮现 → 衰减 → 每 24h 做梦整理 → 晋升」的自动生命周期；hybrid 检索开箱即用；embedding 用本地 BGE-small ONNX（不依赖 PyTorch，数据不出本机），降级链设计优雅（auto → 本地 ONNX → 远程 key → FTS-only）。

hermes-memory-governed 的优势：治理、溯源与极端环境韧性

审查门禁（secret 拦截 + review-required + import_approved 落地）、provenance 溯源（source_rowid 直达 L3 原始消息）、L1 人工规则的治理地位（固定预算不可挤占）、双路径降级（L2 无模型走文本扫描、L3 英文 FTS5/中文 LIKE）——在「记忆可信、可审计、坏环境也能跑」上更强。

一句话

OpenSquilla 把记忆做成了「自动运转的认知系统」；你的项目把记忆做成了「受治理的知识资产管线」。前者赢在自动化与开箱体验，后者赢在可控性、可审计性与部署韧性。两者的强项几乎不重叠——互相借鉴的空间很大。

二、OpenSquilla 记忆系统拆解（据其文档与配置）

存储结构

workspace_dir/                      # 认知记忆层（文件形态）
  MEMORY.md                         # 顶层记忆（人工可编辑）
  memory/*.md                       # 分层记忆文件
state_dir/                          # SQLite 索引（检索层）
migrations/                         # 数据库自动迁移

四层认知记忆 + 生命周期

机制说明（据官方描述与配置）
四层结构工作（working）/ 情节（episodic）/ 语义（semantic）/ 原生（native）——类人记忆的认知科学分层
hybrid 检索向量语义 + 全文关键词混合；retrieval_mode = "hybrid" | "fts_only"
embedding 降级链provider = "auto"：内置 BGE-small ONNX（本地推理）→ memory 专用远程 key → 仅 FTS。支持 openai-compatible / ollama
浮现（promote）热门记忆自动浮现；重要记忆「冒泡」晋升到上层
时间衰减老旧记忆自动衰减
做梦整理（dream）每 24h 后台巩固整理（默认关：enabled=false + preview_mode + auto_schedule=false，安全优先需显式 opt-in）
turn capture对话轮默认写 memory/archive/** 审计转录（不进可检索记忆，index 需显式 opt-in；capture_user=true / capture_assistant=false）
DB 自动迁移migrations/ 目录，schema 版本自动升级

三、hermes-memory-governed 记忆系统拆解（对照）

机制说明（当前代码实现）
L1 手写规则MEMORY.md / USER.md，固定 800 tokens 始终注入，add/replace/remove 语义，60s 缓存
L2 语义记忆LanceDB 向量（384 维 MiniLM，config 化）双路径：向量搜索 / 文本子串扫描；source_rowid 溯源到 L3 消息；NULL 向量自动迁移
L3 归档SQLite + FTS5；英文 FTS5 / 中文 LIKE 降级 / 混合双路合并；abs(rank)/(1+abs(rank)) × 7 天半衰期衰减 → 组内归一化；幂等写入（content_hash）
L4 人格cron 每日从 L1/L2/L3 生成 persona.md，注入系统提示
审查门禁（Bridge）候选 JSONL：secret 模式拦截 + target 白名单 + 追加去重 + 500 行归档；import_approved 把已批准候选落地 L1
召回异步预取（独立临时池 + 超时收集 + 串行降级），MIN_SCORE 过滤，L1 固定预算 800 + L2/L3 共享 1200
知识库管线chat_extractor / meeting_recap / dashboard / knowledge_sync（Obsidian 可选）

四、逐维度对比

维度OpenSquilla 记忆hermes-memory-governed评判
分层哲学认知科学式四层（工作/情节/语义/原生），层间自动流动治理式五层（L1 人工 / L2 语义 / L3 归档 / L4 人格 / Bridge 审查），边界由人工与规则定义哲学不同：自动化 vs 可控性
检索hybrid 开箱即用；FTS-only 一键降级L2 向量/文本双路径 + L3 FTS5/LIKE 双路径（三条链路独立降级）OpenSquilla 集成度更高；governed 韧性更强（极端环境每层都可用）
Embedding本地 BGE-small ONNX（无 PyTorch 依赖）+ openai/ollama 远程可选sentence-transformers（依赖 torch，重）+ 文本降级；模型/维度已 config 化SQ 优 ONNX 路线更轻更省；可借鉴
记忆生命周期浮现 / 衰减 / 晋升 / 每日做梦整理（自动，默认关）时间衰减 + cron persona / health（确定性脚本，无自动晋升）SQ 优 生命周期自动化是它的招牌
写入治理turn capture 审计转录（默认不进检索）+ 合规审批闸门Bridge 门禁（secret 拦截 + 白名单 + 审查落地）+ 幂等写入HG 优 治理粒度更细（按内容拦截而非按轮归档）
溯源决策日志存 hash 不存原文（合规向）source_rowid 直达 L3 原始消息（审计向）场景不同：合规脱敏 vs 知识溯源，各有所长
人机协作MEMORY.md 人工可编辑（机器整理需 opt-in）L1 文件直接手写 + replace/remove 语义；L3 可 SQL 查询HG 优 文件与 SQL 全透明，工程师可控性强
数据可移植SQLite 索引 + workspace 文件，DB 自动迁移全部是本地文件（md / sqlite / lancedb），可 git 管理平手：都是本地优先
宿主形态完整产品（微内核 + 桌面端 + 10+ 渠道 + 网关）Hermes Agent 的可插拔 provider（单一职责）定位不同，不可直接比
维护脚本内置 cron 调度器 + dream 后台任务外部 cron + 确定性脚本（persona / health / retention / rebuild）OpenSquilla 集成度高；governed 更透明可审计

五、可互相借鉴的点

governed 可以从 OpenSquilla 借鉴（按价值排序）

借鉴点现状差距落地建议
ONNX 本地嵌入sentence-transformers 依赖 torch（安装体积大、启动慢）用 onnxruntime 跑 BGE-small（几十 MB，无 torch）作为默认 embedding 后端，ST 降为可选——安装体积和启动时间都会显著改善
记忆浮现 / 晋升机制L2→L1 只能人工审查，无自动晋升给 Bridge 加自动晋升通道：L3 中重复出现 ≥N 次的事实自动生成候选（仍走审查标记），减轻人工筛选拍量
做梦式整理（dream）只有 cron persona 生成，无「记忆重组/压缩」步骤加一个 opt-in 的 dream 任务：定期把 L3 旧会话压缩为语义摘要写回 L2（需人工确认首批输出）
DB 自动迁移schema 变更靠 ALTER 兜底建 migrations 目录 + 版本号，L2/L3 schema 演进可追溯

OpenSquilla 可以从 governed 借鉴（供参考）

借鉴点说明
按内容拦截的审查门禁secret 正则拦截 + target 白名单，比「按轮归档不进检索」的治理粒度更细
provenance 溯源（source_rowid）记忆条目直达原始消息，审计/纠错更快
L1 的治理语义人工规则的固定预算 + replace/remove 语义，比单纯文件更明确
极端环境双路径无模型时文本扫描、无 FTS5 时 LIKE——低配设备也能跑

六、给你的取舍建议

如果你的诉求是…建议
记忆要可信、可审计、给团队/客户用保持 governed 路线，把 P1 剩余项（记忆晋升、dream 压缩）作为后续迭代——治理优势是这个项目的核心价值
想要开箱即用的自动记忆、且在意安装体积借鉴 ONNX 嵌入路线：把 sentence-transformers 换成 onnxruntime + BGE-small，这是单点收益最大的借鉴项
两者都想体验OpenSquilla 是完整 Agent 产品（6.8k stars、Apache-2.0、Python 3.12+），可以直接装来对照它的四层记忆实际表现，再把觉得好的机制搬回 governed

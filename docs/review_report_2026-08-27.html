一、项目概况

Hermes Agent 的分层记忆 provider：L1 手写规则（MEMORY.md / USER.md）、L2 语义记忆（LanceDB）、L3 对话归档（SQLite FTS5）、L4 人格摘要（persona.md），外加 Bridge 人工审查门禁与 Mermaid 短期压缩。设计思路（异步预取读路径 + 非阻塞写路径）是合理的，但核心的 L2 语义层与 L3 时效排序实际不可用，构建配置也无法安装。

二、核心链路现状

L1 手写规则→ L2 语义检索（坏）→ L3 归档（可写，检索弱）→ L4 persona（可用）
层状态问题
L1✅ 可用读取缓存 60s 刷新，逻辑正确；但 replace 语义未实现（与 add 相同，均为追加）
L2❌ 完全失效建表参数错误 + 检索 API 错误 + 无 embedding 向量列，三层错误全部被静默吞掉
L3⚠️ 半可用写入正常；时间衰减是死代码；中文检索基本失效；特殊字符导致查询崩溃
L4✅ 可用由 cron 脚本生成；refresh_l4_background 名不副实（只重读文件）
Bridge✅ 可用脱敏、目标白名单、审查门禁设计良好；但会话启发式提取误报偏多

三、严重缺陷（已实测验证）

严重L2 语义层从创建到检索每一步都失败，且全部静默
plugin/memory_governed/_sync.py :: _init_l2 / _index_l2 · _recall.py :: _search_l2
① create_table(schema={...dict...}) — LanceDB 要求 pyarrow.Schema，dict 直接抛 TypeError；
② 即使表存在，search(query, limit=n) — 正确 API 是链式 .limit(n)，抛 TypeError；
③ 即使修好 API，表没有 vector 列（全项目无任何 embedding 配置），抛 ValueError: "There is no vector column"。
三层异常全部被 except Exception 吞掉 → 运行时零感知，L2 写入永远失败、检索永远返回空。
实测 (lancedb 0.37.1)： create_table(schema=dict) FAILED: TypeError: Schema must be an instance of pyarrow.Schema search(q, limit=5) FAILED: TypeError: LanceTable.search() got an unexpected keyword argument 'limit' search(q).limit(5) FAILED: ValueError: There is no vector column in the data
严重L3 时间衰减是死代码，文档宣称的「7 天半衰期」从未生效
plugin/memory_governed/_recall.py :: _search_l3
公式 math.exp(-0.693 * 0 / decay_hours) 恒等于 1.0；SQL 也从未查询 timestamp 列，衰减系数无从计算。旧对话与新对话排序完全一样。
实测：age_factor = 1.0（无论 decay_hours 取何值）
严重parallel_recall 超时保护双重失效
plugin/memory_governed/_recall.py :: parallel_recall
① as_completed(futures, timeout=0.5) 超时抛 TimeoutError，函数内部无捕获 — governed_search 工具调用直接崩；
② ThreadPoolExecutor 的 with 退出执行 shutdown(wait=True)，即使超时仍阻塞等待慢任务完成 — 配置 0.5s 实际耗时 3s+。
实测：parallel_timeout_seconds=0.5，模拟 L2 慢 3s → 3.00s 后抛 TimeoutError 未捕获
严重pyproject.toml 构建配置错误，项目无法 pip 安装
pyproject.toml :: build-system.backend
setuptools.backends._legacy:_Backend 模块不存在（setuptools 68 无此路径）。正确写法是 setuptools.build_meta:__legacy__。
实测 (setuptools 68.2.2)：BackendUnavailable: Cannot import 'setuptools.backends._legacy'

四、中等问题

高FTS5 中文检索基本失效 + 特殊字符崩溃
_recall.py :: _search_l3（fts_query = " OR ".join(query.split())）
默认 unicode61 分词器按空格分词，中文整句被当单个 token：查询「记得」匹配不到「我记得用户喜欢喝咖啡」；含引号的查询直接 OperationalError（被静默吞掉返回空）。建议：jieba 分词 + AND 组合，或 FTS5 trigram tokenizer（SQLite 3.34+），并对查询做转义。
实测：query='记得' → 0 hits；query='喜欢"咖啡' → OperationalError: unterminated string
高L2 / L3 分数量纲不可比，合并排序失真
_recall.py :: _search_l2 / _search_l3 / parallel_recall
L2 score 约 0~1（LanceDB 距离），L3 score 是 FTS5 rank 绝对值（可达几十）。混排后 L3 几乎永远压过 L2，L2 结果形同虚设。建议按层做 min-max 归一化或 rank 分位转换后再合并。
中on_memory_write 的 replace 分支与 add 完全相同
__init__.py :: on_memory_write
replace 语义应为「定位并替换已有内容」，当前实现只是再次追加（靠去重防重复），无法覆盖/修正已有记忆条目。
中health 脚本退出码过严：warning 即 FAIL
scripts/memory_health_report.py :: main（return 1 if warnings）
「lancedb 未安装」「无候选文件」这类 warning 会让脚本返回 1，导致 daily pipeline 整体报 FAIL，cron 收到误报警。建议 warnings 与 errors 分离，仅 errors 返回非 0。
中配置加载静默失败
_config.py :: load_governed_config
governed_memory.json 解析失败时 except Exception: pass 静默回退默认值，用户配错完全无感知。至少应 log warning 并记录错误详情。
中WriteQueue.stop() 存在竞态且不 join
_sync.py :: WriteQueue.stop
主线程 drain 剩余队列与 worker 线程并发 get 竞争，可能重复处理或漏处理；shutdown 不 join 线程，进程退出时可能丢最后一批 L2 写入。L3 为同步写不受影响。

五、轻微问题与一致性

#位置问题
1_recall.pytoken 估算三处不一致：*3（_truncate_to_tokens）/*4（format_recall）/*4（compress），且未按 CJK/拉丁区分
2_recall.py_handle_audit 用语义搜索当审计查询，不精确；L1/L4 用 substring 匹配，长 ID 会误报
3_sync.pyL3 主表与 FTS 表无外键关联；FTS 插入失败 except: pass → 记录在但永远搜不到；timestamp 类型不一致（REAL vs str）
4__init__.py会话事实启发式过宽（「记得」「以后」高频误报）；每轮 prefetch 新建线程，无线程池复用
5docs/operations.md引用不存在的脚本（wiki_nblm_daily.py 等）；cron 时间表与示例命令不一致；daily pipeline 实际不含 L4 persona 步骤
6memory_pipeline.py--with-notebooklm 指向不存在的脚本，启用即 FAIL
7tests/28 个测试全过但未覆盖 L2 建表/写入/检索、L3 时间衰减、parallel 超时、FTS 中文 — 核心链路无测试保护
8仓库目录无 .git（无法追溯提交历史），位于 github 目录下建议 git init

L2/L3 各自归一化后合并；或按层固定配额，避免 L3 淹没 L2

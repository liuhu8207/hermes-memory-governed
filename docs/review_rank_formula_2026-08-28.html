一、FTS5 rank 语义澄清（修复描述与事实不符）

修复总结的示例表格把「rank 0.001 → 0.999 保留 / rank 10 → 0.091 正确过滤」当作正确行为，但 FTS5 bm25 的语义是：rank 是负数，绝对值越大 = 匹配越好（越相关）。SQL ORDER BY rank 升序就是最相关在前。所以「rank 绝对值 10」代表高度相关的内容，恰恰最不应该被过滤；而 0.001 的弱命中给 0.999 高分反而是错的。此外注释「smaller absolute = more relevant」同样写反了。

二、实测发现的两个问题

问题 11/(1+x) 是递减函数，与「越相关分应越高」方向相反
_recall.py :: _search_l3（score = 1.0 / (1.0 + raw_rank)）
abs(rank) 越大代表越相关，而 1/(1+x) 随 x 增大而减小 → 越相关分越低。当前量级下该问题被掩盖（见问题 2），但语料变大、rank 绝对值到 1~30 时会显现：强相关内容 0.09 分、弱相关 0.99 分。
问题 2（实测确认）真实 rank 量级 1e-6 下，所有结果被映射到 ≈1.0，MIN_SCORE 对 L3 完全失效
同上
实测库中强匹配（python×4）rank=-1.648e-06、弱匹配（python×1）rank=-1.032e-06。1/(1+1.648e-06) ≈ 1/(1+1.032e-06) ≈ 1.0000——两者都约等于 1，强弱的区分度完全丧失，MIN_SCORE=0.1 对 L3 既不误杀也不过滤（形同虚设）。测试表格里「0.001/0.01/0.1」的示例量级与真实 FTS5 rank 相差 3~6 个数量级，方案验证用的假设数据不成立。
实测（强匹配 vs 弱匹配，原始公式）： rank=-1.648e-06 'python python python python deep dive' → score=1.0000 rank=-1.032e-06 'python mentioned once here' → score=1.0000 方向判定: 弱匹配分 0.9999989 略高于强匹配 0.9999984（颠倒，但被 1.0 饱和掩盖）

三、已落地的修复（本轮代码改动）

修复单调递增映射 rank/(1+rank)，方向正确且区分度保留
_recall.py :: _search_l3（score = raw_rank / (1.0 + raw_rank)）
abs(rank) 越大（越相关）分数越高，映射 (0,∞)→(0,1) 有界；与尾部 max 归一化叠加后组内最强恒为 1.0、组内相对差异保留（本例强 1.0 / 弱 0.63）。MIN_SCORE=0.1 从此对 L3 有实际过滤意义（rank≈0 的勉强命中 → score≈0 → 被过滤）。LIKE fallback base 0.5→0.8 的改动保留（精确匹配得分高于模糊匹配，合理）。
实测（修复后）： 强匹配 'python python python python deep dive' → score=1.0000 弱匹配 'python mentioned once here' → score=0.6264 方向判定: ✅ 正确；MIN_SCORE: 两条均保留（都含 python，合理）

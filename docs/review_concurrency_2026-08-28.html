一、总体结论

shutdown 降级、CJK 加权、import 清理都修对了，但并发退化的修复是无效的：DCL（双重检查锁定）解决的是「池的懒创建竞态」，而真正的退化根因是「3 个 worker 被慢任务占满 → 重叠召回的任务排队 → 超时窗口内跑不完 → 空结果」——max_workers 依然是 3，实测第 2 次重叠召回仍返回空。修复描述里自己写了「导致排队等待甚至死锁」，但 DCL 与排队问题无关。

三、无效修复的根因与正确方案

仍在并发退化：慢任务占满 worker → 重叠召回空结果
_recall.py :: _get_pool（DCL）/ parallel_recall（max_workers=3）
时间线：第 1 次召回提交 3 个慢任务（各 2s）→ 超时 0.5s 后主线程返回，但 3 个 worker 仍被占用 1.5s → 第 2 次召回 submit 3 个新任务 → 全部排队 → as_completed 从 submit 起算 0.5s 超时 → 一个都没跑完 → 空结果。
DCL 保证的是「两个线程同时 _get_pool() 不会创建两个池」——这与排队无关（池在首次使用后就一直存在，不存在重复创建）。max_workers=3 意味着任何时刻最多 3 个任务在跑，第二轮召回的任务必须等第一轮的任务结束。
实测（慢任务 2s，超时 0.5s）： 第1次召回: 0.52s, ['P4'] 第2次召回(重叠): 0.51s, [] ← 退化仍在 (等待 2.5s 后) 第3次召回: 正常
正确方案（三选一）：
① max_workers 提到 6+：两轮重叠召回各有独立 worker，互不挤占（最简单）；
② 放弃共享池，每次召回新建池 + pool.shutdown(wait=False)：池间隔离，已实测无线程泄漏、无阻塞（GC __del__ 兜底）；
③ 提交前检查池活跃任务数，忙时直接走 _sequential_recall()。
注意串行降级无超时限制
_recall.py :: _sequential_recall
shutdown 后的召回会串行跑满全部层（实测 4.00s，parallel_timeout_seconds 不生效）。shutdown 后本不该有调用，可接受；但若宿主关停顺序异常，关停过程会被拖长。

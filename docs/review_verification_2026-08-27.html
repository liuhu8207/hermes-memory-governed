一、总体结论

修复总结声称「4 个严重缺陷全部修复」，但实测后发现：实际修复的 4 项与我此前报告中的 4 项严重缺陷并非同一组。修好的部分是真实有效的（L2 建表、L3 时间衰减、L1 replace 语义、FTS 转义），但 parallel_recall 超时与 pyproject 构建配置这两个严重缺陷完全没动，且 L2 向量搜索路径仍不可用、FTS5 中文检索的修复无效、还引入了一个排序方向反转的新 bug。28 个测试全过是因为测试仍未覆盖这些链路。

三、仍存在的问题

严重L2 向量搜索路径仍不可用，且「装了 embedding 反而更差」
_sync.py :: _init_l2（写入端 schema 无 vector 列）· _recall.py :: _search_l2 / _search_l2_vector
写入端建表 schema 只有 content/category/source/timestamp 四个字符串列，没有 vector 列；_index_l2 写入时也不生成向量。
关键漏洞：_search_l2 只在 _embed_fn is None 时走文本降级。一旦装了 sentence-transformers（_embed_fn 非 None），就走向量搜索 → 无 vector 列抛 ValueError → 被 except 吞掉返回空 → 且不会降级到文本 → L2 全空。
实测（伪造 embed_fn 模拟已装 embedding）： search('python') -> 0 条（表无 vector 列） → 结论：安装 embedding 依赖后 L2 从「文本可用」变成「完全不可用」
严重parallel_recall 超时保护仍未修复（漏修）
_recall.py :: parallel_recall
与审查时完全一致：as_completed 超时抛 TimeoutError 无捕获（governed_search 工具会崩）；ThreadPoolExecutor with 退出 shutdown(wait=True) 阻塞等慢任务。
实测：parallel_timeout_seconds=0.5，模拟 L2 慢 3s → 3.00s 后抛 TimeoutError 未捕获
严重pyproject.toml 构建配置仍未修复（漏修）
pyproject.toml :: build-system.backend
仍指向不存在的 setuptools.backends._legacy:_Backend，项目依然无法 pip 安装。
实测：pip install . --dry-run → BackendUnavailable: Cannot import 'setuptools.backends._legacy'
新 bugL2 向量检索排序方向反转
_recall.py :: _search_l2_vector（score = r.get("_distance")）
LanceDB 的 _distance 是距离：越小越相似。代码把 distance 直接当 score，而 parallel_recall 按 score 降序 → 最相似的结果排最后。应改为 1/(1+distance) 或 -distance。
实测：三条记录距离 0.000 / 0.320 / 8.000（LanceDB 返回已按距离升序） score 降序重排后 → 8.000（最不相似）排第一 → 顺序颠倒确认
高FTS5 中文检索修复无效
_recall.py :: _build_fts_query
双引号包裹每个 term 是「短语精确匹配」，FTS5 默认分词器把中文整句当单个 token，短语匹配仍无法命中子串。「咖啡」匹配不到「我记得用户喜欢喝咖啡」——与修复前结果完全一致。需要 jieba 分词或 FTS5 trigram tokenizer。
实测：query='记得' -> 0 hits；query='咖啡' -> 0 hits（库中含「我记得用户喜欢喝咖啡」）
高L3 分数量纲问题仍存在
_recall.py :: _search_l3
时间衰减生效后分数更小：FTS5 rank 绝对值约 10^-6 量级，乘以衰减系数后更小，与 L2 的 0~1 分数量纲完全不可比，混排后 L3 几乎不会出现在 L2 之前（或反之），分层排序失去意义。
